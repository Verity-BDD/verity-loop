## ADDED Requirements

### Requirement: Запуск сервисов при инициализации
Харнесс SHALL запускать сервисы строго в порядке их перечисления в `services`, дожидаясь liveness каждого перед запуском следующего.

#### Scenario: Все сервисы поднялись успешно
- **WHEN** все start-команды выполнены и liveness-проверки вернули HTTP 200 до timeout
- **THEN** харнесс переходит к основному циклу

#### Scenario: Liveness timeout при старте
- **WHEN** сервис не ответил HTTP 200 в течение `liveness.timeout`
- **THEN** харнесс вызывает teardown и завершается с exit 1

### Requirement: Liveness polling
Харнесс SHALL опрашивать `liveness.url` через HTTP GET каждые `liveness.interval` секунд. Сервис считается живым при получении HTTP 200.

#### Scenario: Сервис ответил 200
- **WHEN** HTTP GET на liveness URL возвращает статус 200
- **THEN** liveness-проверка считается пройденной

#### Scenario: Сервис недоступен или вернул не-200
- **WHEN** HTTP GET возвращает ошибку соединения или статус ≠ 200
- **THEN** харнесс ждёт `liveness.interval` и повторяет попытку

### Requirement: Перезапуск сервисов между итерациями
Харнесс SHALL выполнять restart-команды для всех сервисов в порядке списка после каждого завершения агента, с liveness-проверкой каждого.

#### Scenario: Liveness fail после перезапуска
- **WHEN** сервис не прошёл liveness после restart
- **THEN** харнесс останавливает перезапуск оставшихся сервисов и инициирует rollback

### Requirement: Teardown при завершении
Харнесс SHALL вызывать stop-команды для всех сервисов в обратном порядке при любом завершении: успех, неудача, SIGINT, SIGTERM.

#### Scenario: Нормальное завершение
- **WHEN** харнесс завершается с exit 0 или exit 1
- **THEN** stop-команды выполняются для всех сервисов в обратном порядке

#### Scenario: Прерывание сигналом
- **WHEN** харнесс получает SIGINT или SIGTERM
- **THEN** выполняется teardown перед завершением процесса

#### Scenario: Timeout teardown
- **WHEN** teardown выполняется более 10 секунд
- **THEN** харнесс принудительно завершает оставшиеся процессы и выходит

### Requirement: Фоновый запуск start-команды
Start-команда SHALL выполняться харнессом как фоновый процесс. Харнесс не ждёт её завершения, а переходит к liveness polling.

#### Scenario: Start-команда запущена в фоне
- **WHEN** харнесс выполняет start-команду сервиса
- **THEN** команда работает как дочерний процесс харнесса, харнесс не блокируется
