## Context

Новый Go-бинарник `verity-loop` с нуля. Внешних зависимостей от существующего кода нет. Бинарник запускается разработчиком локально, управляет несколькими сервисами через shell-команды и вызывает LLM-агента (по умолчанию `opencode`) как subprocess.

Основные внешние зависимости: git (для снапшотов и диффов), go (для запуска тестов), совместимый агент (opencode или любой бинарник принимающий промпт последним аргументом).

## Goals / Non-Goals

**Goals:**
- Полный цикл: start → test → agent → restart → repeat
- Детерминированный rollback если сервис сломался после изменений агента
- Структурированный цветной лог с чёткими префиксами
- Конфигурация через один YAML-файл
- Агент-агностичный интерфейс: любой бинарник с контрактом `<cmd> <args...> <prompt>`

**Non-Goals:**
- Управление инфраструктурными зависимостями (БД, очереди — предполагаются запущенными)
- Параллельный запуск или перезапуск сервисов
- Глобальный таймаут на весь прогон
- Watch-режим (постоянное наблюдение без итераций)

## Decisions

### D1: Go как язык реализации

Go выбран за простоту сборки в статический бинарник, хорошую стандартную библиотеку для subprocess management (`os/exec`), и естественную обработку сигналов (`os/signal`).

**Альтернатива**: Shell-скрипт — слишком хрупкий для сложной логики rollback и concurrent liveness polling.

### D2: Сервис `start` запускается в фоне, `stop`/`restart` — синхронно

`start`-команда запускается харнессом как фоновый процесс (harness держит `*exec.Cmd` и не ждёт завершения). `stop` и `restart` выполняются синхронно (harness ждёт завершения). Harness отслеживает PID фонового процесса для teardown.

**Альтернатива**: Пользователь сам делает даемонизацию в start-команде. Отклонено — усложняет конфиг, liveness poll уже даёт достаточную обратную связь о готовности.

### D3: Git snapshot через patch-файл во временной директории

Перед каждым запуском агента харнесс сохраняет `git diff` в temp-файл. При rollback применяет `git apply --reverse`. Baseline snapshot (на старте харнесса) хранится отдельно для построения diff-промпта итерации 2+.

**Альтернатива A**: `git stash` — проще, но загрязняет stash-стек пользователя и может конфликтовать с его stash'ами.  
**Альтернатива B**: Копирование файлов вручную — не учитывает удалённые файлы и работает медленно на больших репозиториях.

### D4: Промпт передаётся агенту последним позиционным аргументом

Контракт: `<command> <args...> <prompt_string>`. Промпт собирается в памяти (prompt_file + контекст) и передаётся через `exec.Command` без shell — никаких проблем с экранированием и лимитами длины.

**Альтернатива**: stdin или файл — не задокументировано в opencode, добавляет сложность.

### D5: `--dangerously-skip-permissions` остаётся в `args` конфига

Харнесс агент-агностичен. Специфичные флаги opencode (`--dangerously-skip-permissions`, `--dir`) пользователь добавляет сам через `agent.args` в `verity.yaml`.

**Альтернатива**: Харнесс добавляет специфичные для opencode флаги автоматически — привязывает к конкретному агенту, нарушает агент-агностичность.

### D6: Liveness polling — HTTP GET с таймаутом на каждый запрос

Каждый poll — отдельный HTTP GET с коротким connection timeout (2s). Цикл повторяется каждые `interval` секунд до `timeout`. Логируется каждые N секунд чтобы не спамить, но показывать прогресс.

### D7: SIGINT/SIGTERM вызывают teardown

Харнесс перехватывает SIGINT и SIGTERM, вызывает `teardown()` в обратном порядке сервисов, затем выходит с exit 1. Если teardown занимает более 10s — принудительное завершение.

## Risks / Trade-offs

**[Risk] start-команда завершается сама по себе (краш при старте)** → Harness не детектирует краш процесса между итерациями. Liveness fail покажет проблему косвенно через timeout.

**[Risk] Агент оставляет частичные изменения при timeout** → При rollback `git apply --reverse` может не примениться чисто если агент частично закоммитил. Mitigation: rollback перед новой итерацией, пользователю печатается предупреждение если patch не применился.

**[Risk] `git diff` слишком большой для аргумента** → Теоретически возможно при ARG_MAX. Mitigation: лимит `max_diff_lines` обрезает diff до передачи агенту.

**[Risk] Сервисы не останавливаются если teardown не вызван (kill -9)** → Не решается на уровне харнесса. Инструкция пользователю — добавлять cleanup в системные startup-скрипты.
